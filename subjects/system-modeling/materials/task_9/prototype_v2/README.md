# Прототип ИС ТО и ремонта самолётов, версия после изменения требований

Копия `prototype` с изменением раздела 11 отчёта: вместо ручных повторных попыток при занятых ресурсах введена **очередь ожидания** (FR-14, BR-14, BR-15). Заявка, не получившая ресурсы, встаёт в очередь с нужными ресурсами, интервалом и номером; когда ресурсы освобождаются (отмена заявки, допуск, списание), их автоматически получает первая заявка очереди: выше приоритет, при равенстве – раньше встала в очередь.

Запуск из папки `prototype_v2`:

```
python demo.py
python -m unittest discover -s tests -t . -v
```

`demo.py` показывает те же штатный и неуспешный сценарии, что и в базовой версии; новое поведение проверяют тесты `tests/test_queue.py`.

## Что изменилось по сравнению с `prototype`

Изменено 69 строк кода, прежние тесты не менялись.

| Файл | Изменение (строк) |
|---|---|
| `aircraft_maintenance/domain.py` | `MaintenanceRequest`: 4 атрибута ожидания, `wait_for_resources` с параметрами, `schedule` очищает данные ожидания (12) |
| `aircraft_maintenance/ports.py` | `DataStore.find_waiting_requests` (3) |
| `aircraft_maintenance/storage.py` | Реализация `find_waiting_requests` (7) |
| `aircraft_maintenance/services.py` | `_park` заменён на `_enqueue`, новая `serve_queue`; её вызывают `cancel_request`, `ReleaseService.release`, `WriteOffService.write_off` (47) |
| `tests/test_queue.py` | 8 новых проверок Q1–Q8 (новый файл, 128 строк) |

## Результат

36 проверок (28 прежних и 8 новых), все успешны; вывод – в `test_results.txt`.

## Ограничения

Обслуживание очереди запускается отдельной транзакцией после освобождения ресурсов: между ними другой планировщик может занять освободившийся интервал. Порядок очереди задан одной функцией сортировки в `serve_queue`. Остальные ограничения те же, что у базовой версии.
